**Definition 1 (Gated deploy path).** The deploy path is *gated* iff (i) no apply, push-to-prod, or infra change executes without a human, (ii) every apply is prover-checked behind the human (policy change verified before the pipeline runs it), (iii) runners are generation-rotated with a maximum age in code, and (iv) gate latency is measured and kept boring.

**Theorem 1 (No agent-applied infrastructure).** Under the gated deploy path, no agent — however turned — can apply infrastructure: every apply-shaped action waits at the human gate, and the gate's latency is measured rather than assumed.

*Proof.* Apply rights are the crown jewels, so the gate sits on the apply itself, not on the intent to apply: CI runners propose, humans dispose, and the prover checks the policy change behind the human before anything runs. Generation rotation bounds runner-state accumulation (logs, secrets, prior state flushed on schedule), so a turned long-lived runner loses its foothold on rotation. Gate latency measured and boring means the gate neither blocks legitimate velocity (slow gates get bypassed) nor waves through haste. Find the broadest deploy key, narrow it, verify no agent can apply infrastructure today — and run the guarded preset against staging, because CI speed culture resists gates and only measured latency keeps them honest. ∎
