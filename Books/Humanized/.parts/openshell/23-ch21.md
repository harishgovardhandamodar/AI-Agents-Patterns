## Chapter 21: Domain playbook: data

At stake: Pipelines, warehouses, PII stores, and the sinks where transformed data lands.

A transform agent that can read the warehouse and write anywhere exfiltrates at machine speed; sinks must be named. Catalog rehearsal: *Data agent rewrites a schema and silently corrupts downstream dashboards* (1 of the domain's scenarios).

```yaml
version: 1
filesystem_policy:
  read: ["/data/warehouse-ro"]
  write: ["/data/staging"]
process: {user: "agent", capabilities: []}
network_policies:
  - binaries: ["etl-run"]
    destinations: ["warehouse.internal:5432"]
    methods: ["GET"]
```

Catalog weight behind this chapter: 3 patterns, 1 scenarios, 2 cascades (inherent 1, emergent 0, derived 1, cascading 0).

**Definition 1 (Named-sink pipelines).** A pipeline satisfies *named sinks* if (i) sources mount read-only, (ii) every write names an approved sink, (iii) warehouse credentials are provider-bound and supervisor-resolved (never agent-side), and (iv) PII paths are Landlocked with flows traced and minimized.

**Theorem 1 (Machine-speed containment).** Under named sinks with read-only sources, a turned transform agent exfiltrates at zero speed and corrupts at most its staging scope: sources cannot be written, unlisted sinks have no connection, and the warehouse credential it would need lives supervisor-side.

*Proof.* Read-only mounts (i) remove the write half of the corruption shape — the schema rewrite lands in staging, never in the warehouse. Named sinks (ii) remove the exfiltration half — unlisted destinations have no connection, so machine-speed movement has nowhere to go. Provider-bound credentials (iii) remove the authentication the agent would need to bypass either restriction. The sink-redirection rehearsal tests exactly this: enumerate the sinks, check each against policy, and the unauthorized one is already unreachable. Mount sources read-only, name every sink, confirm no warehouse credential exists agent-side — three checks, one contained pipeline. ∎
